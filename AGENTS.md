# L — инструкции для разработки

## Продукт и границы

L — конструктор произвольных шкафов автоматики на основе расширяемой инженерной базы.
Двигатель — первый тип функционального блока, а не ограничение всего продукта.
Каждый экземпляр на поле независим: id, ответы, сигналы, состав и экземпляры CAD.
Работаем локально. Не восстанавливать `.openai/hosting.json`, не публиковать Sites и
не загружать инженерные файлы во внешние сервисы без новой явной просьбы пользователя.

## Обязательный порядок работы

1. Прочитать `docs/DESIGN.md`, осмотреть текущий код и `git status`. Не затирать чужие изменения.
2. До изменений кратко объяснить пользователю найденную проблему, затрагиваемые модули и результат.
3. Проверить фактические исходники и версию ОЛ. Не подменять источник предположениями или памятью.
4. Внести минимальное связное изменение, добавить регрессионный тест.
5. Выполнить `npm run typecheck`, `npm test`, `npm run test:cad`, `npm run build`.
6. Для UI проверить сценарий в браузере. Для CAD повторно прочитать файл, выполнить аудит,
   визуально проверить результат. Если заявляется совместимость с AutoCAD — открыть именно
   новый экспорт в AutoCAD. Аудит ezdxf и HTTP 200 этого не доказывают.
7. В ответе перечислить сделанное, проверенное и оставшиеся реальные ограничения.

## Инженерная логика

- Единственная точка расчёта — Python `scripts/cabinet_engine.py`.
  UI получает результат через `/api/cad/calculate`; экспорт повторно рассчитывает проект на сервере.
  `tests/reference/*.ts` — замороженный эталон миграции, никогда не подключать его к runtime.
- `order` — адрес в графе ОЛ; `binds` — переходы; `Engine key` — инженерный смысл.
  Никогда не связывать физический смысл с номером строки или числом `order`.
- Импорт Excel — сборочный этап. Runtime читает версионированный JSON, не Downloads пользователя.
- Скрытые ответы не участвуют в расчёте. После изменения родителя удалять недействительные ответы.
- Новая строка ОЛ может расширить существующее правило, но неизвестный новый вид правила требует
  поддержки в движке. Не обещать, что произвольное изменение Excel автоматически станет программой.
- Хранить источник решения: версия/хеш базы, лист, строка, экземпляр блока.
- Нет совпадения, несколько совпадений, неоднозначная граница диапазонов — явная диагностика.
  Не брать произвольно `find()[0]`, не исправлять инженерные данные молча.
- I/O распределять по всему шкафу с учётом дополнительных датчиков и их количества.
  До каталога контроллеров логические номера НЕ называть реальными клеммами или резервом модулей.
- Повторяющийся код шаблона — допустимые разные экземпляры. Запрещён `Set(codes)` для состава шкафа.
- Исторические `motor-engine.ts` и `diagram-selector.ts` не подключать обратно к UI или экспорту.
  Их правила переносить в основное ядро только после проверки источника и тестов.

## CAD

- ДВА независимых документа по ВСЕМ блокам поля: принципиальная электрическая схема
  (`diagram1` в строках ОЛ → `drawingKind=electrical`, рамка Sheet 1.1) и схема внешних
  соединений (`diagram2` → `external`, рамка Sheet 1.2). Не путать колонки diagram1/diagram2
  с листами Excel `diagram 1`/`diagram 2`: каждый из этих листов содержит оба вида схем.
- Не смешивать виды схем в одной полосе. У каждого комплекта свои страницы, рамка и нумерация.
- Привязки рамок и исходная высотная координата задаются в `data/drawing-profiles.json`.
  Изменение рамки требует проверки SHA-256, полей штампа, шин и области размещения.

- В runtime только подготовленные DXF и ezdxf. Конвертация DWG — отдельный офлайн-этап.
- Сборка геометрии не равна выпущенной КД. До внедрения параметризации номиналов, уникальной
  маркировки аппаратов/проводов/клемм, соединений, рамок и штампов экспорт имеет статус DRAFT.
- Нельзя менять надписи, напряжение или номер клеммы глобальным поиском/заменой без контракта шаблона.
- Не считать исправленные EXTMIN/EXTMAX доказанной причиной проблем AutoCAD.
- У экспортов уникальные имена. Проверять GET/HEAD скачивания, Content-Disposition,
  повторные экземпляры, плохие входные данные, недоступный CAD-сервис, устаревший ответ запроса.

## Честная готовность

Не писать «полностью работает», если проверена только сборка фронтенда. Не утверждать, что
проверена вся ОЛ, если просмотрены только примеры. Не расширять эту задачу на публикацию,
изменение оригинальной ОЛ, удаление файлов или переписывание всего интерфейса без основания.
