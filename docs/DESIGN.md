# Как проектировать L дальше

## 1. Целевая задача

Уточнение от 10.09: из полного состава поля выпускаются ДВА комплекта — принципиальная
электрическая схема и схема внешних соединений. В UI есть две отдельные ссылки DXF и общий ZIP.
Колонка `diagram1` любой строки ОЛ определяет принципиальный фрагмент; колонка `diagram2` —
внешние соединения. Лист `diagram 2` — дополнительные сигналы, а не обозначение вида документа.

Рамки из исходного `Схемы.zip` отдельно конвертированы офлайн: Sheet 1.1 содержит шины питания,
Sheet 1.2 — зону «ШКАФ». В runtime AutoCAD не вызывается. `drawing-profiles.json` хранит
проверенные хеши, исходные координаты и сигнатуры полей штампа. Фрагменты раскладываются по ширине,
как в ВЕРСА, с переносом на следующие листы. Высотная привязка сохраняется относительно исходной
рамки, чтобы не сдвигать цепи относительно шин. Счётчик листов независим для каждого документа.
Для внешних соединений профиль задаёт общий сдвиг вверх на 10 мм: в исходных координатах
клеммная строка находилась ниже зоны «ШКАФ» рамки Sheet 1.2. Между фрагментами оставлено 8 мм,
чтобы соседние обозначения не касались друг друга. Это параметры компоновки, не изменение схемы.

В исходной рамке Sheet 1.2 обнаружены 20 HATCH за пределами её A3. Только при сборке рабочей копии
они исключаются по проверенному профилю; оригинальный DWG и конвертированный DXF не переписаны.
Электрические соединения, перенумерация клемм и замена всех номиналов не считаются завершёнными:
для этого нужен контракт точек подключения/атрибутов каждого фрагмента. Метод ВЕРСА (хеш источника,
handle, ожидаемый тип/текст) принят как правило безопасной параметризации, но её карты клемм
от старых Э5-блоков нельзя применять к новым im/bm/pr-шаблонам.

Новые пользовательские DWG `im1-011…014` заменяют прежние источники этих кодов. Их DXF
получены через AutoCAD Core Console. При импорте рабочей копии исключаются 23 старые HATCH,
расположенные отдельно от фрагмента; хеш источника и handles записаны в контрактах шаблонов.
Для четырёх вариантов координата на листе задаётся опорной надписью `ХТ1` в контрактах;
фрагменты одной группы размещаются рядом по ширине рамки с общей высотной привязкой.
Для принципиального комплекта этих четырёх кодов источник теперь раскладывается на
три проверенные по handles части: все силовые цепи шкафа, затем управление, затем
обратная связь. Номера QF/KM и клеммы назначаются один раз для исходного экземпляра.
Два пересечения между обратной связью и управлением в PNP-вариантах оформлены
парными ссылками `NET-N` с номерами листов; остальные коды остаются целыми
фрагментами на отдельных листах. Контракт и ограничения — в
`docs/CAD_CIRCUIT_GROUPING.md`.
Отдельный контракт на каждый код привязывает MTEXT-поля: QF/KM, зажимы ХТ1,
совместимый по ОЛ DI/DO, их общие выводы и три наименования из строк `diagram head` ОЛ.
Лист `Поля схем Э3` таблицы маркировки задаёт роль каждого PLC-поля, ключ DXF и колонку
выбранной строки вывода. Так `DI24-PNP` может получить `01/GND1` или `U1/GND3`, а
`DOT-PNP` использует отдельное поле общего вывода. Если на листе тот же `PLC:GND`
уже показан, повторная изолированная ветвь удаляется целиком по перечисленным в контракте
пяти объектам; следующий фрагмент ставится с зазором 2 мм. Когда в одном фрагменте обе
ветви стали `GND3`, сохраняется исходная ветвь `#GND3`. Это удаление повторного изображения;
межфрагментные электрические сети и связи с внешней схемой пока не рассчитываются.
Если I/O назначен модулю, его поля в основном фрагменте остаются неразрешёнными,
а в принципиальный комплект добавляется отдельный лист M1…M5 с ведомостью
назначенных сигналов, клемм и общих выводов из расчёта. Пока нет проверенного
CAD-шаблона модуля, этот лист не является его электрической схемой;
назначения также остаются в расчёте и manifest.
Экспорт остаётся DRAFT.

Пользователь собирает состав шкафа из функциональных блоков и задаёт требования через опросники.
Система должна выбрать оборудование, собрать спецификацию, назначить реальные I/O, маркировку,
провода и клеммы, затем выпустить согласованную КД. Ограничение — инженерная база и поддержанные
виды правил, а не зашитый список типов шкафов. Инженер задаёт правила; программа применяет их
одинаково к каждому экземпляру и объясняет результат.

## 2. Текущая структура

| Уровень | Файлы | Ответственность |
|---|---|---|
| Источник | `data/rules-source`, оригинальные ОЛ | Редактируемые инженерные таблицы |
| Импорт | `scripts/extract_motor_rules.py` | Проверка графа, JSON со строками-источниками и SHA-256 |
| Интерфейс | `app/page.tsx`, `app/globals.css` | Поле, опросник, просмотр результата, скачивание |
| Граф вопросов | `scripts/questionnaire.py` | Серверная видимость, обязательность, ввод, исключение скрытых ответов |
| Расчёт шкафа | `scripts/cabinet_engine.py` | Единственный runtime-движок: экземпляры, схемы, количества, диагностика, спецификация |
| ПЛК и I/O | `scripts/extract_plc_rules.py`, `scripts/io_allocator.py` | Каталог M245 и тестового M245 no display; выбор числа модулей и распределение без повторного занятия вывода |
| Клиент API | `lib/engineering-client.ts` | Типы данных, запрос расчёта, отмена устаревших ответов, отображение состояния запроса |
| HTTP-мост | `app/api/cad/[...path]/route.ts` | Same-origin доступ к закрытому CAD-процессу |
| CAD API | `scripts/local_cad_api.py` | Валидация, лимиты, уникальные результаты и скачивание |
| CAD-сборка | `scripts/assemble_dxf_package.py` | Повторные экземпляры DXF, компоновка, сохранение, повторное чтение |

Технологии: TypeScript, React, Tailwind, Vinext/Vite для интерфейса и HTTP-моста;
Python для опросника, инженерного расчёта и CAD через ezdxf; JSON-снимки правил только на сервере.
Это пока не система с серверной БД: проекты и рабочие области сохраняются только в браузере
конкретного устройства, результаты генерации — на диске сервера. При первом открытии новая
структура переносит прежний локальный черновик в «Текущий проект» → «Рабочая область 1».
Для закрытого стенда есть две серверные учётные записи: хеши паролей и ключ подписи сессий лежат
в root-доступном environment-файле, не в репозитории. Вход защищает расчёт и файлы CAD; роли,
серверное проектное хранилище и аудит действий пока не реализованы. До HTTPS это не защищённый
канал для пароля.
Веб-приложение не хранит параллельных движков подбора: единственный runtime-источник
инженерного расчёта — `scripts/cabinet_engine.py`.

## 3. Контракт правил Excel

- `order` уникален во всех Ques-листах; `binds` содержит существующие коды через `;`.
- Отрисовка следует графу, не номерам строк. При переносе вопроса меняются `order` и все его ссылки.
- `Engine key` связывает ответ с измерением `diagram1.start/location/voltage/trip` или дополнительным
  сигналом `diagram2.*`. Новые инженерные роли должны получить явный ключ.
- Для ещё не размеченных количеств и полей есть `data/motor-field-bindings.json`:
  сопоставление по листу и названию вопроса. Это временный явный адаптер, а не привязка к `order`.
  Переименование такого вопроса требует обновления адаптера либо заполнения Engine key в ОЛ.
- Изменение XLSX вступает в силу после импорта JSON и перезапуска Python. Отпечаток расчёта
  включает хеши ОЛ, состава ПЛК и таблицы ключей; устаревший результат нельзя экспортировать.
- Импорт Ques и двух листов `diagram` ищет колонки по заголовкам. `Load index` и `sp`
  пока читаются по позициям: переставлять их без обновления/проверки импортера нельзя.
- Новая строка существующей таблицы поддерживается текущим алгоритмом; новая формула, тип входа
  или логический оператор требуют реализации, версии схемы данных и тестов.
- Границы диапазонов не интерпретировать молча. Пока обе границы включены, пересечение даёт
  диагностику. Правило полуинтервалов/приоритета должен определить инженер и зафиксировать в базе.

## 4. Один расчёт — все представления

`scripts/cabinet_engine.py:calculate_cabinet` возвращает независимые блоки, выбранные строки, назначенные выводы M245,
предварительный состав, экземпляры CAD, ошибки, предупреждения и хеш правил.
Опросник и экспорт не пересчитывают схемы отдельно. У каждой вставки свой id, даже если code совпадает.
Ошибки обязательного ввода блокируют общий экспорт. Незавершённый блок не пропадает незаметно.
Изменение ответов сбрасывает ранее показанные ссылки; запоздалый ответ генерации не становится
результатом новой конфигурации. Ранее скачанный файл остаётся отдельным снимком.

Расчёт выполняется в Python. POST `/api/cad/calculate` принимает `{motors}` (id, tag, state),
возвращает `{calculation, forms, revision}`. `forms` содержит только видимые вопросы, без `binds`
и `engineKey`; полные таблицы ОЛ не включаются в JS. UI пересчитывает через 250 мс после ввода,
отменяет предыдущий запрос, принимает только ответ для текущего проекта и сохраняет очищенные
сервером ответы. Пока результат устарел или сервис недоступен, экспорт блокируется.
POST `/api/cad/generate` принимает тот же проект, текущий `ruleFingerprint` и необязательный
`blockId`. Сервер заново вызывает тот же движок, проверяет полноту шкафа и сам строит manifest.
Клиентские `instances` не используются. Устаревшая ревизия получает HTTP 409.
В выгрузке сохраняется снимок расчёта. Это пока не БД ревизий и не разграничение пользователей.
`tests/fixtures/engine-cases.json` — замороженные входы и ожидаемые результаты Python-движка.
Они проверяют регрессии без второй реализации инженерной логики и не импортируются в приложение.

## 5. Что уже есть, а что ещё нельзя обещать

Есть повторяемые моторы, динамический опросник, выбор основных/дополнительных схем, количества
датчиков, распределение выводов M245, повторяющиеся DXF-фрагменты и скачивание. Load index 1 и sp4 связаны
для однозначных совпадений; sp3 учитывает экземпляры датчиков.

Не завершено:

1. Полная инженерная приёмка всех ветвей ЧП. Реализованы ручной подбор sp1,
   автоматический Load index 2 → sp2 с запасом, внешний ЧП по входному току;
   регрессионные примеры не доказывают полноту всех исходных таблиц.
2. Полная проверка базы и графа по всем веткам. В текущем графе несколько веток могут открывать
   одноимённые поля тока/мощности. Различающиеся ответы дают ошибку; саму инженерную связь уточнить в ОЛ.
3. Подключён контроллер ZENTEC M245 с 35 ресурсами и до пяти тестовых модулей
   `M245 no display` по 21 ресурсу из `moduls`/`add_cond`. Модуль трактуется как расширение
   по явному указанию пользователя для теста; аппаратная совместимость и реальные клеммы
   ещё не подтверждены паспортом. Его ключи находятся на листе `Клеммы модуля тест`.
   Подбор схем и выводов идёт по всему шкафу: точное сопоставление проверяет занятость
   физического ресурса отдельно для PLC/M1…M5, затем выбирает минимум модулей; среди
   допустимых размещений глобальная оптимизация сначала занимает менее универсальные
   выводы. Адрес выводится с обозначением устройства (`PLC:01`, `M1:01`). Для схем
   `im1-011…014` модульные поля сохраняются неразрешёнными и добавляется отдельный
   подписанный лист назначений модуля без вымышленной геометрии. Цена и резерв модулей пока не рассчитаны.
   При равенстве вариантов сохраняется предпочтение PNP/транзисторного DO; электрический
   выбор нужно подтвердить инженерно.
4. В рабочей копии ОЛ `diagram 2!R5:R7` и `R8:R10` задают одинаковый расход
   `AI-RTD2`: 1/2/3 для 2/3/4-проводного подключения. Исправлены `R6: 3→2` и
   `R7: 4→3`; прежняя версия сохранена отдельным файлом в Downloads. Обе группы в этом листе — Pt100:
   датчики обмотки и подшипников.
   Имя кода и количества в строках не доказывают схему подключения реального входа.
5. Параметризация CAD: для слоёв `QF`, `KM`, `KL` уже реализована безопасная сквозная
   нумерация маркеров `#N`/`#N.M` в порядке блоков шкафа с удалением `#` в выгрузке; все замены записываются в manifest
   выгрузки с handle исходного поля. Номиналы, номера проводов/клемм, межлистовые ссылки,
   цепи питания, рамки, штампы, paperspace, PDF и полный выпуск КД ещё не параметризованы.
6. Импорт пользовательского УГО: сейчас выбирается только имя файла; такая конфигурация блокируется,
   чтобы выгрузка не притворялась, что геометрия добавлена.
7. Серверное хранение ревизий, права, очередь задач и полноценная БД. Локальные проекты и
   рабочие области уже сохраняются в браузере, но не синхронизируются между устройствами.

Надпись DRAFT возле фрагмента — метка экземпляра компоновки, не электрическая перенумерация.
Подготовка слоёв и маркеров `#` описана в `docs/CAD_TEMPLATE_PREPARATION.md`; одинаковый
маркер на `XT*` или `Headers` не считается обозначением аппарата и не изменяется.
Аудит ezdxf подтверждает структурную читаемость, не правильность схемы и не открытие в AutoCAD.
Известную проблему открытия нужно воспроизводить на конкретном файле в самом AutoCAD.

## 6. Следующие этапы в правильном порядке

1. Эталон: один полностью согласованный мотор от ОЛ до реальной схемы и спецификации.
2. Контракт CAD-шаблона: код/версия, mm, габариты, точки соединений, параметры, допустимые значения,
   атрибуты, список фиксированных надписей и проверка их соответствия варианту.
3. Разделить тип блока и экземпляр. Добавить стабильные fieldId/optionId независимо от порядка UI.
4. Проверить правила индекса нагрузки и ЧП на крайних значениях; закрыть все пробелы BOM.
5. Ввести модель электрических сетей и уникальные обозначения. Геометрия рисует уже рассчитанные сети.
6. Каталог PLC и аппаратных модулей → проверяемое распределение → реальные клеммы → CAD/BOM.
7. После проверки одного блока — два одинаковых, разные пуски, датчики с количеством, смешанный шкаф.
8. Сохранение ревизий, пользователи и права. Серверный расчёт уже реализован;
   многопользовательское развёртывание требует следующих механизмов хранения и доступа.

## 7. Готовность изменения

Минимум: typecheck, unit-тесты, Python-тесты, production build. Регрессионные сценарии:
пустой/частично заполненный шкаф, два одинаковых мотора, 3 датчика, отключение родительской ветки,
недопустимый ввод, неизвестный код, повторный id, аналоговые сигналы, параллельные экспорты,
изменение ответа во время генерации, скачивание файла и его повторное чтение.
Отдельно проверить браузер, внешний вид CAD и открытие в целевом CAD-приложении.

## 8. Серверная эксплуатация

Веб-процесс и Python-процесс расчёта/CAD запускаются отдельно. `L_DXF_INTERNAL_URL` у веб-процесса указывает
на закрытый CAD endpoint; `L_DXF_BIND_HOST`/`L_DXF_PORT` задают привязку Python. Браузер не знает
адрес CAD-сервиса. Каталог `output/generated` должен быть постоянным томом с политикой хранения.

Для публичного продакшена пока необходимы авторизация/проверка владельца выгрузки, лимиты запросов
на reverse proxy, очередь задач, TTL и квота файлов, журнал ошибок, резервное
копирование проектов. UUID в ссылке не заменяет права доступа. Сейчас запуск предназначен для
MVP. Текущий VPS обновляется только по явному поручению пользователя; Sites не используется.
