# Порядок принципиальных схем по цепям

Статус: реализовано для `im1-011…014` в принципиальном комплекте. Исходные DXF
остаются целыми; их проверенные объекты перечислены по частям в
`data/cad-template-contracts/im1-011…014.json`. Остальные схемы пока выводятся
отдельной группой `other` целыми фрагментами. Простой разрез DXF по координате
не применяется: он может перерезать провод.

## Что остаётся одним функциональным блоком

Экземпляр двигателя сохраняет один `blockId`, ответы ОЛ, выбранный вариант, аппараты,
сигналы и назначенные I/O. Для принципиальной схемы вариант разворачивается в три
логические части:

| Часть | Содержание | Общее между вариантами |
|---|---|---|
| `power` | Питание двигателя, силовые полюса QF/KM, силовые зажимы ХТ1 и PE | Возможно одна геометрия после сверки четырёх DXF |
| `control` | Выход ПЛК, цепь катушки KM, общий вывод выхода, если нужен | Вариант DOR-NO или DOT-PNP |
| `feedback` | Вспомогательный контакт QF, вход ПЛК и его GND | Вариант DI24-NPN или DI24-PNP |

Исходные сочетания: `im1-011` = DOR-NO + DI24-NPN, `im1-012` = DOR-NO +
DI24-PNP, `im1-013` = DOT-PNP + DI24-NPN, `im1-014` = DOT-PNP + DI24-PNP.
Это карта выбора частей, а не разрешение механически копировать геометрию одного
варианта в другой.

## Расчёт и раскладка

1. `cabinet_engine.py` выбирает варианты для всех блоков и `io_allocator.py`
   назначает выводы всего шкафа. Выбор не зависит от положения фрагмента на листе.
2. Для каждого блока создаются три части с одним `blockId`. Обозначения QF и KM
   выделяются один раз и используются во всех частях этого блока. Адрес ПЛК и
   обозначение GND берутся из одной выбранной строки листа `Ключи зажимов ПЛК`:
   `entrance number 1/2` (E/F) и `CND_COM` (D). Префикс `PLC`/`M1` хранится
   отдельно как принадлежность устройства и не добавляется к тексту клеммы в DXF.
3. Сборщик размещает по всему шкафу сначала `power`, затем `control`, затем
   `feedback`. Внутри каждой группы сохраняется порядок блоков на поле. Каждая
   группа переносится на следующие листы по доступной области рамки; номер листа
   и межлистовые ссылки вычисляются после раскладки.
4. В `im1-012` и `im1-014` один конец провода обратной связи совпадает с концом
   провода управления. Эти два соединения записаны в `interpartConnections` по
   handles и координатам исходного DXF. После разделения на обоих листах
   ставится одинаковая метка `NET-N` и номер встречного листа; manifest хранит
   обе точки. Если объект, конец провода или исходный хеш изменились, сборка
   останавливается. У `im1-011` и `im1-013` пересечений между частями нет.
5. Повторный GND на одном листе удаляется вместе с его проверенной ветвью по
   прежнему контракту. Полная модель межлистовых сетей, включая питание и
   внешние соединения, ещё не реализована; экспорт остаётся DRAFT.
6. Схема внешних соединений остаётся отдельным документом `diagram2`; её нельзя
   смешивать с этими тремя частями принципиальной схемы `diagram1`.

## Данные, необходимые для безопасного разделения

Текущий контракт хранит исходный хеш DXF, роль части, полный список entity
handles и встречные концы проводов. Сборщик сверяет полноту разбиения,
принадлежность полей и все совпадающие концы LINE разных частей. Порядок частей
пока задан кодом для четырёх моторных вариантов; для расширения на другие
шаблоны нужна инженерная карта их цепей и соединений. Габариты и опорная
точка вычисляются из исходного DXF, а не из изменяемой строки Excel.
